# Rule 26 step 6: files already over the line, pinned at their current size.
#
# One `<lines> <path>` per row. A file listed here may SHRINK but not GROW --
# `check-file-sizes.sh` fails if it exceeds its ceiling, and fails on any file
# not listed here that crosses 500 lines. That is the whole point: the ten
# scanners below are not getting smaller today, but nothing new joins them and
# none of them creeps.
#
# Shrinking a file below its ceiling is good news, not a failure: the check
# says so and asks you to tighten the number here (or `--update` does it).
# Drop the row entirely once a file is back under 500.
#
# A ceiling moving UP needs a reason in the commit that moves it. So far:
#   files.ts 591 -> 615 (2026-11-12) — `isVirtualenv`, a `pyvenv.cfg` test in
#   the directory walk. It belongs in the file whose job is file collection,
#   and Rule 26 step 1 says split by responsibility, not by line count; a new
#   file for one 6-line predicate would be the worse mistake.
#   community.ts 3049 -> 2968 the same day, by moving calibration out.
#   community.ts 2968 -> 2973 (2026-11-13) — a `steps` counter on
#   LinearMatcher, so the ReDoS tests can assert on work done instead of
#   elapsed milliseconds. Instrumentation for a class belongs on that
#   class; the 5 lines cannot be moved anywhere that makes sense.
#
# A SPLIT adds a row, which is the one case where the list grows. Rule 26
# step 7 asks for the split and step 6 fails on any new file over 500, so a
# giant cut in two usually trips its own guard -- the gate's error message
# names the remedy: list it in the same commit and say why in TODO.md.
#   community.ts 2973 -> 1623 and linear-regex.ts 1383 (2026-11-13), the
#   linear-time matcher moved out whole. 2973 -> 3006 across the two files,
#   +33 lines (1.1%) of header and import, which is the cost of the seam.
#   Each half keeps its own ceiling so each can only shrink; the sum is NOT
#   the thing guarded, because a sum lets one half grow while the other
#   shrinks and still reports green.
#
